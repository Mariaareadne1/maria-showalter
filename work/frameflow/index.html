Case study · macOS app · 2026

From screen capture to a considered product film.

FrameFlow records a Mac screen through a native capture helper, finds the moments that matter from where you clicked and paused, and re-frames the recording around them — then exports exactly what the preview showed, as MP4 or GIF.

01 — Journey

Record, find the moments, compose, export.

The whole product is one path, and each step exists in code today. You never edit a keyframe unless you want to: the recording arrives already framed, and everything after that is a decision about taste.

  1. Record

    Pick a display or a window, system audio, a countdown. A floating HUD (or ⌘⇧2) stops it.

  2. Moments

    Clicks and pauses become camera moves, each shown as a card with a real thumbnail and an honest label — “Click at 0:08”.

  3. Compose

    Five art directions, four camera feels, four cursor treatments, captions and arrows, cuts on a timeline.

  4. Export

    MP4 from 720p to 4K at 30 or 60 fps, or a looping GIF — written to a temporary file and renamed only when complete.

02 — Constraint

A raw recording shows everything at once.

A full-screen capture of a 1920-pixel display, watched in a 700-pixel embed, turns the interesting part — a button, a field, a number changing — into a few dozen pixels. The usual fix is manual: scrub, keyframe a zoom, ease it, keyframe the way back out, repeat for every click. That labour is why most demos are either static or over-produced.

FrameFlow's bet is that the recording already knows where the attention is. The helper excludes the system cursor from the pixels and records the pointer separately at 60 Hz with every click, on the video's own clock. That telemetry is enough to infer the camera, and to redraw the cursor cleanly at any zoom.

03 — Interaction

A canvas-first studio built around Moments.

The Studio keeps the film large and the controls in a dock beneath it. Moments are the unit of editing: a card per camera move, which you can rename, retime, re-aim, disable, delete or add at the playhead. Anything you touch is promoted from automatic to manual, so changing the camera feel later regenerates only the moves you haven't claimed.

The five art directions on the same instant of the same export (time code 00:00:10.517 burned into the test footage), taken from MP4s produced by the test suite. Same zoom, same cursor, different room.

04 — System

Four processes, one renderer.

The capture runs in a small Swift program, not in Electron, because ScreenCaptureKit and AVAssetWriter are native APIs and the writer must keep pace with 60 fps. It speaks JSON lines on stdout and takes stop on stdin. Electron's main process owns files and permissions; the renderer never touches the disk directly — 29 typed IPC channels, each handler validated and checked against the sender. Every frame anyone sees, in preview or in a file, comes from one function: renderFrame.

05 — Decisions

Three choices that carry the product.

The camera is a function of time, not a simulation.

Cursor and camera paths are baked once, at 120 Hz, into typed arrays using a critically damped smoothing step; the position at any time is a lookup. Nothing depends on the previous frame, so scrubbing, preview and export land on the same framing.

The camera follows a leashed target: it only moves by however far the pointer strays beyond a dead zone, so a hand settling on a button never nudges the shot. Zooms less than 0.8 s apart are chained, so the camera pans from one moment to the next instead of zooming out and back in.

src/shared/engine/cursor.ts · camera.ts

// cursor.ts — the camera target only moves past the dead zone
for (let i = 0; i < count; i++) {
  const p = sampleRaw(samples, i * dt)!
  const dx = p.x - tx
  const dy = p.y - ty
  const dist = Math.hypot(dx, dy)
  if (dist > deadzone) {
    const k = (dist - deadzone) / dist
    tx += dx * k
    ty += dy * k
  }
  leashed[i] = { t: i * dt, x: tx, y: ty }
}
return buildSmoothPath(leashed, duration, smoothTime)

One renderer for preview, thumbnails, MP4 and GIF.

renderFrame draws the backdrop, the rounded frame, the zoom, the vector cursor and its treatment, and captions. The preview hands it a <video> element; the exporter hands it a decoded frame. A zoom is a crop of the source rectangle, so zoomed frames use full-resolution pixels, and every size is derived from the output's short side, so a 960-pixel preview and a 4K export are the same picture.

The exporter samples each output frame at the middle of its interval, mapped back through any cuts, encodes with WebCodecs, and streams 8 MB chunks to a .partial file that is renamed only on success — cancelling leaves nothing behind.

src/renderer/src/engine/render.ts · media/exporter.ts

// exporter.ts — sample each frame mid-interval, through cuts
export function framePlan(segments, fps) {
  const total = outputDuration(segments)
  const count = Math.max(1, Math.round(total * fps))
  return { count, sourceTimeAt: (i) =>
    outputToSource(segments, (i + 0.5) / fps) }
}

A redesign that cannot change old exports.

Version 2 rebuilt the editor and the camera model, which put every project saved by 0.1 at risk. One parser, parseProject, now runs on every load and before every save, so a renderer bug can't persist a corrupt file. Old projects keep their stored zooms verbatim and are pinned to the 0.1 tuning; the first save keeps a .v1.bak; writes are atomic and queued per file so an autosave can't race a rename.

Project files are treated as untrusted: a path inside one is only opened if it is a real media file in the library, beside the project, or the project is in Recents.

src/shared/projectModel.ts · src/main/projects.ts

// projects.ts
export async function saveProject(path, project, thumbnail) {
  const p = assertProject(path)
  // Validate before writing so a renderer bug can never
  // persist a corrupt project.
  const clean = parseProject(project)
  if (!isReadable(clean.media.path))
    throw new Error('Project references a file that was not granted.')
  await withFile(p, () => writeProjectFile(p, clean, …))
}

// Writes to the same file are serialized.
function withFile(p, fn) {
  const next = (fileQueues.get(p) ?? Promise.resolve()).then(fn, fn)
  fileQueues.set(p, next.catch(() => undefined))
  return next
}

07 — Evidence

What is tested, and what isn't.

Recordings are hard to test because they need permission, a screen and a moving mouse. FrameFlow's helper has a synthetic mode that renders a moving pattern, a scripted cursor and test tones through the same writer, and the test videos carry a burned-in time code that the suite reads back from exported frames. That makes most of the pipeline testable without a person at the machine.

08 — Reflection

What I'd keep, and what's next.

Keep: making the camera a pure function of time. It is what made a shared renderer possible, and the shared renderer is what made the preview trustworthy. Most of the hard bugs were found by measuring exported frames rather than looking at them — a 0.23× camera jump between chained zooms, colour banding from a 444 palette in GIFs, window audio that was silently −91 dB.

Trade-off: the cursor is always redrawn as a vector arrow. That is what lets it stay crisp at 2× zoom and wear a halo or spotlight, but it means real cursor shapes (I-beams, resize handles) are not captured yet.

Next: verify the microphone path on hardware, add a webcam layer, and sign and notarize a release so it can be installed without a Gatekeeper exception.
