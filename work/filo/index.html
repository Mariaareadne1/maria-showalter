Case study · mobile product · 2026

Places worth going, from people you trust.

Filo is a map of a single campus where every pin belongs to a person you know. Instead of anonymous stars, places are ranked by comparison — is this better or worse than somewhere you've been? — and the people whose rankings line up with yours become your taste twins.

There are no screenshots of the mobile app on this page. Every screen depends on a live Supabase project, and the only way to fill one with demo content writes fake accounts into a real database — so rather than stage that, the interactive pieces below run the app's own ranking and matching code, ported line for line, and are labelled as explainers. The story of how Filo started is on the blog.

01 — Premise

A screenshot of a friend's list beats a five-star average.

Review platforms answer “is this place good?” for an imaginary average person. The question students actually ask each other is narrower: would you like it? — and the best answer usually comes from a friend whose taste you already know. Filo is built around that, with three deliberate refusals written into its design rules: no public star ratings or numeric scores, no sponsored or algorithmic feed, and a feed that stops instead of scrolling forever.

The core loop in the code today:

  • Pin a place found through Google Places, as visited or want to go, with a photo and a one-line impression.
  • Rank visited places by comparing them with ones you've already ranked.
  • Collect pins into boards you can reorder and share.
  • Follow classmates — sign-in is limited to campus email domains, and private accounts require approval.
  • See a map of your pins, your friends' or the whole campus, a feed of friends' pins, and your taste twins.
02 — Interaction

Ranking by comparison, in about log₂(n) taps.

Scores invite inflation: everything good becomes a 9. A ranking forces a choice, but dragging a new café into a list of thirty is tedious. Filo asks one question at a time about the place in the middle of the candidates that are left, and each answer halves them — a binary search the user performs with their taste. Try it: you are adding a new café to a list of seven.

Where does Tamsin go?

Your cafés, best first. Answer as you like — the list narrows to the places still in contention.

    Explainer: fictional cafés · the step function is nextCompareState from lib/rankInsert.ts, unchanged

    “Haven't been” is treated as worse so an unknown comparison can't stall the search, and “about the same” gives the new item the shown place’s position, just ahead of it. The function is pure and covered by unit tests; on the server, the result is written by a single database function (below) so a half-finished re-rank can never leave two places sharing a position.

    03 — Taste twins

    Agreement measured on what you've both ranked.

    Two people are compared only on the places both have ranked, and only when they share at least three. Each person's ranks are first re-ranked within that overlap — so a friend whose list is twice as long isn't penalised for it — and then scored with Spearman's rank correlation, clamped so that disagreement reads as 0 % rather than a negative number.

        04 — System

        Privacy lives in the database, not the client.

        The mobile client talks directly to Supabase, so the rules about who can see what cannot live in the app — anyone can call the API with their own session. Row-level security policies, triggers and a handful of database functions carry those rules. Places come from Google Places; the map is Mapbox; a separate Next.js app holds shared-board pages and an early dashboard for venues.

        05 — Decisions

        Three things the database does so the app doesn't have to.

        Re-ranking is one transaction.

        Inserting a place at position 3 shifts everything below it. Done from the client, that was a series of separate updates that could interleave or fail halfway. It now happens inside one database function: an advisory lock serialises re-ranks for the same person and category, and the uniqueness of (person, category, position) is checked only at commit, so positions may collide mid-transaction while rows shift.

        supabase/migrations/…_data_layer.sql

        PERFORM pg_advisory_xact_lock(hashtext(v_user::text), hashtext(p_category));
SET CONSTRAINTS rankings_user_id_category_position_key DEFERRED;
DELETE FROM rankings
  WHERE user_id = v_user AND place_id = p_place_id AND category = p_category;
-- close the gap, clamp the target, open a slot, insert
WITH ordered AS (
  SELECT id, row_number() OVER (ORDER BY position) AS rn
  FROM rankings WHERE user_id = v_user AND category = p_category)
UPDATE rankings r SET position = o.rn FROM ordered o WHERE r.id = o.id;
SELECT count(*) INTO v_count FROM rankings
  WHERE user_id = v_user AND category = p_category;
v_pos := greatest(1, least(v_pos, v_count + 1));
UPDATE rankings SET position = position + 1
  WHERE user_id = v_user AND category = p_category AND position >= v_pos;
INSERT INTO rankings (user_id, place_id, category, position)
  VALUES (v_user, p_place_id, p_category, v_pos);

        The server decides whether a follow is pending.

        A private account's pins are visible only to followers it has accepted. If the app wrote the follow's status, any client could write “active”. Instead the app omits it, and a trigger sets it from the target's privacy setting; another trigger makes the two people in a follow immutable. Pin visibility policies then trust only that server-set status.

        supabase/migrations/…_security_hardening.sql

        CREATE OR REPLACE FUNCTION set_follow_status() RETURNS trigger
LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
BEGIN
  SELECT CASE WHEN u.is_private THEN 'pending' ELSE 'active' END
    INTO NEW.status FROM users u WHERE u.id = NEW.following_id;
  IF NEW.status IS NULL THEN
    RAISE EXCEPTION 'Target user does not exist';
  END IF;
  RETURN NEW;
END; $$;

        Venue analytics that can't single anyone out.

        The venue dashboard shows a business how students found it. Every number is computed only from public pins by public accounts, and any count below three people is suppressed — a k-anonymity floor — so a small venue can't infer an individual's behaviour. A review pass on this code caught a LEFT JOIN whose filter would have leaked private rows; the fix moved the privacy predicate into an inner join, with a comment explaining why.

        supabase/migrations/…_phase2_discovery_rpcs.sql

        select 'board'::text, board_reach.board_name, board_reach.reach::integer
from board_reach
where board_reach.reach >= k_anon      -- suppress small cells
union all
select 'follow'::text, 'word-of-mouth chain'::text, chain.n
from ( select count(distinct recent.user_id)::integer as n
       from pins recent join users ru on ru.id = recent.user_id
       where recent.place_id = p_place_id and recent.is_public = true
         and ru.is_private = false
         and recent.created_at >= now() - interval '7 days'
         and exists ( … a followed friend pinned it earlier … ) ) chain
where chain.n >= k_anon;
        06 — Search model

        A natural-language search experiment, kept honest.

        Alongside the app I built a small semantic search service: type “late night ramen after drinks” and get venues back by meaning rather than keywords. It fine-tunes the all-MiniLM-L6-v2 sentence embedding model with a contrastive loss, using hard negatives drawn from categories people easily confuse (a wine bar versus a cocktail bar), serves cosine-similarity search from FastAPI, and has a small React front end.

        Three things matter for reading it fairly:

        • The data is synthetic. The pipeline tries a live venue API and falls back to generated venues; the catalogue committed to the repository is 500 of 500 generated, with templated descriptions — some reuse real New York venue names at random locations, so its results are not real recommendations.
        • The evaluation is at ceiling. On its own metric (MRR@5, where a hit means the right category) the base model already scores 1.0 on the validation queries, as does the fine-tuned one, and the validation queries are also used in training. Re-measured for this page; it shows the pipeline works end to end, not that fine-tuning helps.
        • It is not connected to Filo. The app's “saved by people like you” lens is a SQL query over overlapping rankings, not this model.

        Run locally for this page: the health check responds, and the ramen query returns three ramen shops from the synthetic catalogue (top similarity 0.587); an out-of-range request is rejected by validation.

        08 — Reflection

        What I'd tell myself at the start.

        Put the rules where they can't be bypassed. Moving ranking and follow privacy into the database removed whole classes of client bugs, and made the app simpler.

        Test the boundaries, not just the logic. The pure functions are well tested; the places this audit found problems are the joins between layers — two category vocabularies, policies versus queries. Policy tests against a local database are next.

        Be strict about what a demo proves. The search model is a good learning project and a working pipeline. It isn't evidence of better recommendations until it's evaluated on real places with held-out queries.
